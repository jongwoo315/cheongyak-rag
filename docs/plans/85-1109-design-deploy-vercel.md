**Notion:** #85 · **선행:** #83(trace), #84(화면·HTTP API) · **바꾸는 stub:** 「배포(#85)」 — 지금은 로컬에서만 뜬다

## jw 기준

vercel neon으로 배포가 성공하고, 배포된 사이트에서 주택청약 검색 및 조건 확인을 할 수 있다

## Vercel + Neon을 고른 근거

- jw가 2026-11-09에 골랐다. 근거는 「계속 쓸지 모르니 무료로 시작한다」
- 비교한 셋(2026-11-06~09 조사, 월 비용은 추정)
  - Railway: 약 $15. 코드 그대로. 아시아는 싱가포르뿐
  - Fly.io: 약 $29. 코드 그대로. 도쿄
  - Vercel Hobby + Neon Free: $0. 코드를 서버리스에 맞게 고쳐야 한다
- DB를 Supabase가 아니라 Neon으로 한 이유: Supabase 무료는 1주 동안 안 쓰면 프로젝트가 멈추고 대시보드에서 다시 켜야 한다. Neon 무료는 5분 뒤 컴퓨트만 멈추고 다음 쿼리 때 수백 ms 안에 켜진다. 방문이 뜸한 데모에는 Neon이 맞다
- Vercel은 자체 Postgres를 더 이상 제공하지 않는다. Marketplace로 Neon을 붙인다. Neon은 모든 플랜에서 pgvector를 쓸 수 있다(문서 기준 PG17에 0.8.0)

## 구성

```
브라우저
  │
  ▼
Vercel 프로젝트 ① web  (루트 web/, Next.js, 리전 sin1)
  │  서버에서만 API_BASE_URL로 호출
  ▼
Vercel 프로젝트 ② api  (루트 repo, FastAPI = Python 함수, 리전 sin1)
  │  DATABASE_URL (Neon 직접 연결)
  ▼
Neon Postgres 17 + pgvector  (싱가포르)
```

- Vercel 프로젝트 둘. Next.js와 FastAPI를 한 프로젝트에 섞지 않는다 — #84가 이미 `API_BASE_URL`로 나눠 두었다
- 리전은 함수와 DB를 맞춘다. 판정 한 번에 DB 쿼리가 여러 번 나가서 함수와 DB 사이 지연이 쌓인다. Neon에 서울·도쿄가 없어 싱가포르로 맞춘다
  - Hobby에서 `sin1`을 고를 수 있는지는 문서에 명시가 없다. 배포 때 안 되면 함수 기본 리전(`iad1`)에 맞춰 Neon을 미국 동부로 만든다. 그 결정은 배포 때 jw가 하고 리포트에 적는다
- Neon은 직접 연결(pooler가 아닌 주소)을 쓴다. 판정 흐름이 `SET LOCAL hnsw.*`를 쓰고, pooler(PgBouncer transaction 모드)는 세션 `SET`을 지원하지 않는다. 트래픽이 적어 연결 수는 문제가 안 된다(추정)

## 서버리스라서 바꾸는 것

| 지금 | 서버리스에서 일어나는 일 | 바꾸는 것 |
| --- | --- | --- |
| 캐시 파일을 `data/cache/`(패키지 옆)에 이어 쓴다 | 함수 파일 시스템은 `/tmp` 말고는 쓰기가 안 된다(추정, 문서에 명시 없음). 첫 판정이 `OSError`로 실패한다 | 환경 변수 `CACHE_DIR`로 캐시 위치를 바꾼다. 기본값은 지금 경로. 배포는 `/tmp/cheongyak-cache` |
| 요청 제한이 없다 | 주소가 공개되면 판정마다 LLM 비용이 든다(질의당 약 $0.05, #80 실측에서 계산) | 하루 판정 한도. DB 테이블 하나로 한국 날짜별 판정 수를 센다. 넘으면 429 |
| `_LOCK` 대기 시간에 제한이 없다(#84 리뷰 지적 13) | 앞 판정이 길면 뒤 요청이 함수 시간 제한(300초)까지 묶인다 | 대기 시간 제한. 넘으면 503 「다른 판정이 진행 중」 |
| 화면→FastAPI 호출에 시간 제한이 없다(지적 12) | Vercel이 300초에 함수를 끊으면 브라우저는 원인 없는 오류를 본다 | 라우트 핸들러에 시간 제한. 넘으면 504와 안내 문구. `catch`가 원인을 로그에 남긴다 |
| 200인데 본문이 JSON이 아니면 화면이 예외로 멈춘다(지적 11) | 플랫폼 오류 페이지가 끼면 나온다 | 화면이 오류 문구를 보여 준다 |
| `DATABASE_URL`이 `postgresql+psycopg://` 꼴이어야 한다 | Neon·Vercel이 주는 값은 `postgresql://` 꼴이다 | 설정이 `postgres://`·`postgresql://`를 `postgresql+psycopg://`로 바꿔 읽는다 |

**하루 판정 한도.** 한도 안에서는 캐시 적중이든 아니든 판정 요청 하나를 하나로 센다(DB 행 쓰기 한 번). 없는 공고(404)·모순된 프로필(422)은 세지 않는다 — #84에서 trace 행 전에 멈추는 자리와 같다. 기본값 50, 환경 변수로 바꾼다. 50 × $0.05 = 하루 약 $2.5가 비용 상한이다(추정). <!-- style-exempt -->

- IP별 제한은 넣지 않는다. Next.js 서버가 FastAPI를 부르므로 FastAPI가 보는 IP는 Vercel 서버 것이고, 진짜 IP를 넘기면 그 값은 위조할 수 있다. 하루 한도로 돈은 막힌다. 대신 누군가 한도를 다 쓰면 그날은 데모가 판정을 못 한다 — 받아들인다
- OpenAI 대시보드의 사용 한도는 jw가 따로 건다(코드 밖 안전장치)

## 데이터 옮기기

- Neon에 스키마는 `alembic upgrade head`로 만든다(pgvector 확장, HNSW 인덱스 포함)
- 데이터는 로컬 컨테이너에서 `pg_dump --data-only`로 테이블을 골라 뽑는다. `traces`·하루 판정 한도 테이블·`alembic_version`은 옮기지 않는다
  - `traces`는 로컬 측정 기록이다. 배포 사이트는 빈 `traces`로 시작한다
- 로컬 `psql`은 14라 pg17 서버를 못 덤프한다. 덤프와 적재 둘 다 `docker exec cheongyak-db`(pg17 클라이언트)로 한다
- 옮긴 뒤 테이블마다 행 수를 원본과 대조한다. 하나라도 다르면 멈춘다
- 대상이 로컬 `cheongyak` DB면 스크립트가 거부한다. 로컬 원본은 읽기만 한다

## 배포 사이트에서 jw 기준을 재는 법

배포 주소로 #84의 측정(`web/e2e/measure.spec.ts` + `web_report.py`)을 다시 돌린다. 측정 코드는 `WEB_BASE_URL`을 이미 받는다.

- 배포 성공: api `/health`가 200이고 `db`·`pgvector`가 `ok`. web `/`가 200
- 검색: 공고 목록에서 공고를 찾아 들어가는 것으로 읽었다(지금 화면에 검색창은 없다). #84의 F(공고 페이지 84개 중 실패 수)·L(목록의 공고 링크 수)을 배포 주소에서 잰다. 기대값은 로컬 DB에서 만든다 — 옮긴 뒤 행 수가 같다는 것을 적재 스크립트가 이미 확인한다
- 조건 확인: #84의 18쌍(공고 6건 × 프로필 3종)을 실제 브라우저로 배포 사이트에 질의한다
  - G1. 정해진 시간 안에 결과가 안 뜬 쌍 수. 배포는 캐시가 비어 있어 LLM을 실제로 부른다. 대기 시간은 240초(Vercel 함수 제한 300초 안쪽)
  - G2'. 결과가 떴는데 **화면의 경로 키 집합 또는 체크리스트 항목 수**가 기대값(`runs/81` 답)과 다른 쌍 수. 판정값은 비교하지 않는다
  - 판정값을 빼는 이유: #84는 캐시를 그대로 읽어 #81과 같은 답이 나와야 했다. 배포는 캐시가 비어 LLM을 새로 부르고, 같은 프롬프트라도 판정값이 바뀔 수 있다. 경로 키와 체크리스트 항목은 공고 사실에서 정해지는 쪽이라 LLM과 무관하다(추정, 측정에서 확인한다)
  - 판정값이 #81과 같은 쌍 수는 같이 적는다. 구간은 없다
- 측정 비용: 18쌍 × 약 $0.05 ≈ $0.9(추정). 하루 판정 한도 50 안이다

## 범위 밖

- 직접 산 도메인 연결. 무료로 시작하므로 `*.vercel.app` 주소를 쓴다. 도메인 구입은 jw가 정한 뒤 별도로
- IP별 요청 제한, 로그인
- CI·GitHub 연동 자동 배포. 이번은 CLI로 배포한다. 연동은 OAuth 권한을 주는 일이라 따로 정한다
- 캐시를 배포에 같이 싣기. 캐시를 실으면 측정이 캐시만 읽어 실제 사용자가 타는 LLM 경로를 못 잰다
- 동시 판정. 인스턴스 안에서는 여전히 한 번에 하나다. Vercel이 인스턴스를 늘리면 인스턴스끼리는 동시에 실행된다(잠금이 인스턴스 사이에는 안 걸린다). 캐시 파일이 인스턴스마다 따로라 문제는 없다
