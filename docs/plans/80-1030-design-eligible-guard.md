# #80 재시작 — 프로필 값 없이 ELIGIBLE을 내지 못하게 막는 코드 guard

**Notion:** #80 · **이전 시도:** PR #12(닫음, 커밋 `1c06665`) · **바탕 설계:** `docs/plans/80-1029-design-axis-verdict.md`(판정 흐름·판정값 5개·설계 결정 표·측정 표본은 그대로 쓴다)

## jw 기준

빈 프로필을 eligible로 판정하지 않고, 꽉 찬 프로필에 없는 값을 있다고 eligible로 판정하지 않는다

## 왜 다시 하나

PR #12는 자동 기준 7/7을 채웠지만 PR 게이트에서 반려됐다(`docs/decisions.md` #80 행).

- 빈 프로필(`empty.json`)인데 `ELIGIBLE` 7개 — 재당첨 3 · 특별공급 유형 2 · 거주 2
- 꽉 찬 프로필(`full.json`)에서 프로필에 칸이 없는 4개 축(`residence`·`income_asset`·`rewin`·`special_type`)의 `ELIGIBLE` 13개. 예: 거주지역 칸이 없는데 이유에 「프로필의 공급지역이 경기로 확인되어」라고 썼다
- 구현 루프가 system 프롬프트를 세 번 고쳤다. 빈 프로필 쪽 10→5→6→7, 꽉 찬 쪽(ELIGIBLE·INELIGIBLE 합) 24→18→15→18로 방향 없이 오르내렸다. 프롬프트로는 0이 안 나왔다

## 무엇을 바꾸나 — LLM 응답 뒤에 규칙 하나

PR #12의 판정 모듈을 그대로 가져오고, 인용 guardrail 다음에 규칙 하나를 더한다.

```
LLM 응답 → 인용 대조(기존 guardrail 넷) → [새] ELIGIBLE guard → Verdict
```

**`ELIGIBLE`은 그 축을 판정하는 데 필요한 프로필 칸에 값이 전부 있을 때만 남는다.** 아니면 `NEED_INFO`로 바꾸고 `guarded=True`, 원래 판정은 `original_verdict`에 둔다.

| 축 | 필요한 프로필 칸 | 근거 |
| --- | --- | --- |
| `homeless` | `homeless_now` | 무주택세대구성원 판정 값. #77이 사용자가 끝낸 판정으로 받는다 |
| `account` | `savings_join_date` | 가입 기간을 #77 `score`가 이 값으로 셈한다 |
| `householder` | `is_household_head` | — |
| `residence` | (#77에 없음) | 거주 지역·기간 |
| `income_asset` | (#77에 없음) | 월평균 소득·자산 |
| `rewin` | (#77에 없음) | 과거 당첨 이력 |
| `special_type` | (#77에 없음) | 유형별 자격. 모든 유형이 거주·소득·당첨 이력 중 하나 이상을 본다 |

- 필요한 칸이 #77에 없는 4개 축은 프로필이 꽉 차도 `ELIGIBLE`이 나올 수 없다. 원래 설계 §프로필에 없는 칸이 「이 네 축은 `NEED_INFO`가 정상 답」이라고 이미 적었다 — 그 문장을 코드로 옮긴다
- 빈 프로필은 모든 칸이 비어 7개 축 전부에서 `ELIGIBLE`이 나올 수 없다. 빈 프로필용 규칙을 따로 두지 않는다
- `need_info`는 guard가 채운다. 위 표의 근거 칸 문구(「거주 지역·기간」 등)를 쓴다. LLM이 단 인용은 그대로 둔다(`NEED_INFO`도 인용 1개 이상 규칙)
- `INELIGIBLE`은 건드리지 않는다. PR #12에서 칸 없는 축의 `INELIGIBLE` 5개는 프로필에 실제로 있는 값(혼인신고일·미혼 자녀 수)에서 나왔다. jw 기준도 `ELIGIBLE`만 다룬다

## 설계 결정

| 항목 | 고른 것 | 안 고른 것과 이유 |
| --- | --- | --- |
| 막는 자리 | LLM 응답 뒤 코드 규칙 | 프롬프트를 더 고치기. PR #12에서 세 번 고쳐 0이 안 나왔고 값이 오르내렸다. 규칙은 축·칸 표 하나라 결과가 정해진다 |
| 막는 단위 | 축 하나 × 필요한 칸 목록 | 이유 문장에 프로필 칸 이름이 나오는지 검사. 문장 검사는 「프로필의 공급지역」처럼 지어낸 칸 이름도 통과시킨다 |
| 바꾼 값 | `NEED_INFO` | `UNVERIFIABLE`. 근거는 찾았고 모자란 것은 프로필 값이라 설계 §판정값 표의 `NEED_INFO` 뜻이다 |
| system 프롬프트 | **고치지 않는다** | 고치면 캐시 키가 바뀌어 135회를 다시 부른다(~$0.93). 그대로 두면 LLM 원 판정이 PR #12와 바이트까지 같아 guard 효과만 따로 보인다 |

## 측정

- 표본·프로필은 PR #12와 같다(공고 6건 × `full`·`partial`·`empty`, 켜진 하위 질의 135개)
- 프롬프트를 안 고치므로 첫 실행은 캐시 135개 적중, API 호출 0회가 기대값이다
- 리포트에 두 값을 나란히 싣는다: guard 전(LLM 원 판정)과 guard 후(최종 판정). guard 전 값이 PR #12 측정값(빈 프로필 ELIGIBLE 7, 꽉 찬 프로필 칸 없는 축 ELIGIBLE 13)과 같아야 같은 응답을 읽은 것이다

### 결과를 읽을 때

- guard는 축 단위 규칙이라 표본에 맞춰 다듬은 것이 아니다. 하지만 측정 표본에서 0이 나오는 것은 규칙의 정의상 당연하다 — jw 기준 0은 「규칙이 빠짐없이 걸렸다」는 확인이지 「LLM이 지어내지 않게 됐다」는 뜻이 아니다. LLM 원 판정의 지어낸 값은 guard 전 값으로 따로 보인다
- guard가 지나치게 넓으면 정상 판정을 지운다. 꽉 찬 프로필은 `homeless`·`account`·`householder`의 칸이 다 있으므로 이 세 축에서 guard가 바꾼 판정은 0이어야 한다
