# #84 화면 — 설계

**Notion:** #84 · **선행:** #83(trace 저장, PR #16 머지 `18f01c4`) · **바탕 설계:** `docs/plans/0727-design-cheongyak-rag.md` §6 스택(프론트 = Next.js SSR, 「공고별 페이지 인덱싱 → 롱테일 검색 유입. SPA면 이 경로가 통째로 없음」)

## jw 기준

next js 서버가 잘뜬다, 유저입장에서 청약별로 질의를 하고 결과를 확인할 수 있다

## 왜

- 지금 판정은 CLI로만 쓸 수 있다(`uv run python -m cheongyak_rag.generate.verdict <공고> --profile <json>`). 사용자가 프로필 JSON을 손으로 만들어야 한다
- #85 배포는 사람이 브라우저로 쓰는 화면을 전제로 한다. 화면이 없으면 배포할 것이 없다
- 공고 84건마다 서버에서 그린 페이지가 있어야 검색 엔진이 공고 이름으로 찾아 들어온다(바탕 설계 §6)

## 흐름에서의 자리

- 이미 있는 것: 공고 값 → 축 켜고 끄기(B4) → 축별 검색(B5) → LLM 판정(B6) → 인용 대조·ELIGIBLE guard(B7) → B8 집계 → B9 응답 → trace 행(#83). 진입점은 CLI `verdict.main` 하나이고, 그 안에서 `trace.run_traced`를 부른다
- 이번에 바꾸는 stub: 「화면·HTTP API(#84)」(#83 설계 「남는 stub」)
- 이번에 더하는 것: FastAPI에 공고 조회 2개·판정 1개 HTTP API, `web/`에 Next.js 앱(공고 목록, 공고 페이지, 프로필 입력, 판정 결과)
- 남는 stub: B9b 질문 랭킹(#82, 응답의 `questions`는 빈 목록 그대로), 배포·요청 제한(#85)

## 정한 것

| 항목 | 고른 것 | 안 고른 것과 이유 |
| --- | --- | --- |
| 데이터 경로 | **Next.js는 FastAPI만 부른다.** 공고 목록·공고 상세·판정 모두 HTTP API로 받는다. Node 쪽에 DB 드라이버를 두지 않는다 | Next.js가 Postgres를 직접 읽기. 공고 칸 해석이 파이썬(`axes`·`asof`)과 TypeScript 두 곳으로 갈라진다. 판정은 어차피 파이썬이라 API가 필요하다 |
| 판정 API | `POST /api/notices/{house_manage_no}/verdict`, 본문은 프로필 JSON(#77 칸 그대로). 안에서 `trace.run_traced`를 부른다 — CLI와 같은 함수라 질의마다 trace 행이 하나 생긴다 | 새 판정 함수. #83 설계가 「#84 HTTP API도 이 함수를 부르게 된다」고 정했다 |
| 판정 API 오류 | 프로필 형식 오류 422 · 없는 공고 404 · `TRACE_HASH_KEY` 없음 503(흐름 전) · OpenAI 하드 오류 503 · 행 쓰기만 실패하면 200에 응답과 `trace_error`를 같이 싣는다 | 행 쓰기 실패를 500으로. #83 설계 「사용자에게 줄 답을 기록 실패 때문에 버리지 않는다」를 그대로 따른다 |
| 브라우저 → 판정 | 브라우저는 Next.js의 같은 주소(`/api/verdict/...` 라우트 핸들러)로 보내고, Next.js 서버가 FastAPI로 넘긴다 | 브라우저가 FastAPI를 직접 부르기. CORS 설정과 API 주소 노출이 생긴다 |
| 공고 페이지 | `/notices/[houseManageNo]`를 서버에서 그린다(SSR). `<title>`에 공고 이름, 공고 정보(지역·주소·공급 세대·모집공고일·접수 기간·당첨자 발표일·청약홈 링크)와 주택형 표가 JS 없이 HTML에 들어 있다. 공고 84건은 `house_manage_no`가 전부 다르다(실제 DB `count(distinct)` 84) | 브라우저에서 그리기(SPA). 검색 엔진 유입 경로가 없어진다 |
| 공고 목록 | `/`에 84건 전부, 모집공고일 순. 공고 페이지 링크 | 지역 필터·검색. 84건이면 한 화면으로 충분하다 |
| 프로필 입력 | 공고 페이지 안의 입력 칸 15개(#77 `Profile` 칸). 참·거짓 칸은 「예 / 아니오 / 모름」, 날짜는 `<input type="date">`, 수는 숫자 칸. 빈 칸과 「모름」은 JSON에서 뺀다(`Profile`에서 `None` = 모른다) | 단계별 질문 화면. 질문 랭킹(#82)이 생긴 뒤에 본다 |
| 입력 값 유지 | 브라우저 `sessionStorage`에 둔다. 다른 공고 페이지로 옮겨도 다시 안 친다. 탭을 닫으면 사라진다. 서버에는 저장하지 않는다(바탕 설계 「프로필은 서버에 저장하지 않는다」) | 매번 다시 입력. 「청약별로 질의」하려면 공고를 옮길 때마다 15칸을 다시 쳐야 한다 |
| 결과 화면 | 전역 판정, 신청 가능한 경로, 경로별 판정 표(일반공급 + 특별공급 유형), 가점 범위, 체크리스트(축·질의·판정·이유·조건·필요한 정보·코드가 바꾼 사실·검색 밖 언급, 근거 원문은 접어 두고 출처·링크). 판정 중에는 「판정 중」 표시 | 판정값만. jw 기준의 「결과를 확인」은 왜 그 판정인지까지 보는 것이라 체크리스트와 근거가 있어야 한다 |
| 화면 꾸밈 | 순수 CSS 한 파일. UI 라이브러리를 넣지 않는다 | Tailwind·컴포넌트 라이브러리. 페이지가 셋이라 의존성 비용이 더 크다 |

## 측정

- 서버가 뜬다: `next build` → `next start`, FastAPI도 같이 띄운다. 공고 84건 페이지를 JS 없이 HTTP로 받아 200인지, `<title>`에 공고 이름(`notices.house_nm`)이 있는지, 주택형 표 행 수가 실제 DB `notice_models` 행 수와 같은지 본다. 기대값은 측정 코드가 실제 DB를 따로 읽어 만든다
- 질의하고 결과를 확인한다: 실제 브라우저(Playwright Chromium)로 #81과 같은 18쌍(공고 6건 `runs/79/last_run.json` × 프로필 3종 `runs/80/profiles/`)을 사람이 하듯 입력 칸을 채워 보낸다. 화면에 나온 전역 판정·경로별 판정·체크리스트 항목 수를 #81 측정 결과(`runs/81/last_run.json`의 같은 쌍 `answer`)와 맞춰 본다. 기대값이 이 티켓 코드와 무관한 이전 측정 파일이다
- LLM 호출 수: 판정 캐시(`data/cache/verdict-gpt-5.4-mini.jsonl`)는 프롬프트 전체가 키다. 화면 입력이 JSON 프로필과 같은 `Profile`을 만들면 18쌍 전부 캐시에서 읽혀 호출이 0이다. 호출이 생기면 입력 칸 → JSON 변환이 어딘가 다르다는 뜻이다
- trace 행: 화면 질의 18건이 실제 DB `traces`에 새 행 18개를 남긴다
