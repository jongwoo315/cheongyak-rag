## 「#131에서 놓친 검색」 두 묶음

jw 기준의 「놓친 검색」은 글자 그대로 읽으면 #131이 놓친 것 전부다. #131에는 놓친 것이 두 묶음 있다.

| 묶음 | 무엇 | 개수 | 「찾았다」의 뜻 |
| --- | --- | --- | --- |
| A. 점검 run | 조문 첫 문장 질문 20개 중 자기 조가 1위가 아니었던 것 | BM25 1 · dense 3 (4건, 조로는 3개) | 그 retriever에서 자기 조가 1위 |
| B. golden | #131 hybrid에서 hit@5 = 0인 문항 (정답 조가 하나도 상위 5개에 없음) | 123문항 중 20개 | 후보의 hybrid hit@5 = 1 |

「개선된 청킹」은 #73의 `article` 외 후보 넷(`paragraph` · `paragraph+head` · `item` · `item+head`)으로 읽는다.
어느 후보를 「개선된」으로 볼지는 jw 기준이 정하지 않았다 — 리포트는 넷 모두 값을 낸다.

## 범위

### 1. 묶음 A — 후보별 점검 run

- `evaluate.pick_sanity`·`first_sentence`로 #131과 같은 질문 20개를 만든다(바꾸지 않는다)
- 후보마다 `chunk.law_chunks` → BM25·dense 청크 순위 → `chunk_eval.article_ranks`로 조 순위 셋
- 질문마다 남길 것: 후보, 조, bm25·dense·hybrid 자기 순위, 각 1위 조, 자기 조에서 가장 높이 오른 청크의
  `path`와 글자 수, 질문 글자 수, 그 청크에 질문 문장이 글자 그대로 있는지
- `article` 후보 값이 `runs/sanity/results.jsonl`과 같아야 한다(재현)

### 2. 묶음 B — golden 놓친 20문항

- `runs/hybrid/results.jsonl`에서 hit@5 = 0인 문항, `runs/73/<후보>/results.jsonl`에서 같은 문항의 hybrid
  hit@5와 정답 조 순위. 반대 방향(#131이 맞혔는데 후보가 놓친 문항)도 같이 센다
- 새 run을 돌리지 않는다

### 3. 원인 — `article`에서 놓친 4건

조 단위에서 왜 다른 조가 1위로 올라왔는지를 숫자로 적는다.

- BM25(제59조): 질문 낱말마다 자기 조와 1위 조(제58조의4)의 점수 기여(idf × tf 항), 두 조의 토큰 수와 평균 토큰 수
- dense(제9조·제45조·제59조): 질문과 자기 조·1위 조의 코사인, 두 조의 글자 수(조문 글자 수 중앙값 672.5자 대비),
  자기 조 안에서 질문과 코사인이 가장 높은 청크(`item` 후보 기준)의 코사인
- 원인 문장은 이 숫자에서 나온 것만 쓴다(예: 「자기 조 2502자, 중앙값의 3.7배」)

### 4. #131 리뷰 1차 #9 defer — 테스트 둘

- `evaluate_run`이 낸 줄을 그대로 `compare.build_report`에 넣어 리포트가 만들어지는 통합 테스트(가짜 임베더)
- `Embedder`(캐시 파일을 tmp에 둔다, 가짜 OpenAI 클라이언트)로 `write_run`을 두 번 돌려 두 번째 API 호출 0회,
  `results.jsonl` 바이트 동일
