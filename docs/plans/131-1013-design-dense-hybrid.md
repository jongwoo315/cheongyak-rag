## 이 티켓이 맡는 범위

#131 페이지의 범위는 검색 비교·abstain·citation·generator provider 2종 비교까지다. jw 기준은
**검색 비교**만 말한다. 이 PR은 검색 쪽만 하고 나머지는 후속 티켓으로 넘긴다(§이번에 안 하는 것).

- 질문: 국토부 청약 FAQ의 질문 (#70)
- 찾을 대상: 주택공급에 관한 규칙 현행 조문 88개 (#69, 삭제 조문 2개 제외)
- 정답: 그 FAQ 답변이 인용한 규칙 조문
- 비교: BM25 / dense / hybrid(둘을 RRF로 합침) 세 run. 본 비교는 dense와 hybrid다.
  BM25 run은 hybrid가 왜 그렇게 나왔는지 읽으려면 있어야 해서 같이 돌린다

## 정답 라벨 — FAQ 인용을 그대로 쓴다

FAQ 답변은 국토부가 쓰면서 근거 조문을 붙였다. 그 인용을 정답으로 쓰면 사람이 라벨을 만들지
않아도 되고, BM25나 dense 결과로 정답을 만든 것이 아니라서 비교가 데이터 구성에 오염되지 않는다
(rag-lab 설계가 MIRACL-ko를 뺀 이유와 같다).

### 실측 (2026-10-13, main 세션)

- FAQ 480쌍 중 조문을 인용한 쌍 182, 인용한 조가 전부 현행 규칙 번호에 있는 쌍 142
- 142쌍의 정답 조 개수: 1개 83쌍, 2개 30쌍, 3개 18쌍, 4개 이상 11쌍
- 가장 많이 인용된 조는 제53조 48쌍, 제4조 15쌍, 제2조 14쌍이다
- 질문 글자 수 중앙값 45자. 질문에 `제N조`가 직접 들어간 것 26쌍
- 조문 글자 수(항·호·목을 이어 붙인 것) 중앙값 696자, 90% 3030자, 최대 3859자

### 문제 — FAQ의 `cited_articles`에는 법령 이름이 없다

#70 파서는 답변의 `제N조`를 법령 구분 없이 모았다. 그래서 「주택법」 제2조도 규칙 제2조로 잡힌다.
142쌍 안에서 인용 바로 앞 40자에 다른 법령 이름이 보이는 인용이 43개였다(정규식으로 센 값,
손 검수 없음). 예: 66번 쌍의 제2조는 「주택법」 제2조다.

### 정한 것 — 인용마다 법령을 붙인다

답변 원문에서 인용 자리마다 바로 앞의 법령 이름을 찾아 셋으로 나눈다.

| 분류 | 조건 | 정답에 넣나 |
| --- | --- | --- |
| 규칙 | 가장 가까운 법령 이름이 「주택공급에 관한 규칙」·「주택공급규칙」·「같은 규칙」·「동 규칙」·「이 규칙」 | 넣는다 |
| 다른 법령 | 가장 가까운 법령 이름이 그 밖의 법·령·규칙 (「주택법」·「같은 법」·「영」 등) | 안 넣는다 |
| 이름 없음 | 같은 문장 안에 법령 이름이 없다 | 넣는다. FAQ가 청약 FAQ라 이름 없는 인용은 규칙으로 본다 |

- 질문에 정답이 하나도 안 남으면 그 질문은 빼고 이유를 센다
- 규칙으로 분류됐는데 그 조가 현행에 없으면(삭제·개정으로 사라짐) 그 질문은 뺀다 — 정답이
  코퍼스에 없으면 어느 run도 못 맞혀 차이가 흐려진다
- 「이름 없음 = 규칙」은 가정이다. 리포트에 이름 없음 인용 수와 표본 20개(인용 앞 60자)를 찍어
  PR 게이트에서 눈으로 볼 수 있게 한다

`제N조` 단위로 묶는다(항·호는 뗀다). 조 하나가 문서 하나라서 정답도 조 단위다.

## 문서 단위 — 조 하나 = 문서 하나

- 문서 텍스트: `제N조(제목)` 머리 + 조문 본문 + 항·호·목 본문을 순서대로 이은 것
- 가장 긴 조가 3859자라 `text-embedding-3-small` 입력 한도(8191 토큰) 안에 들어간다
- 항 단위로 자르면 정답이 조 단위라 「같은 조의 다른 항」을 어떻게 셀지가 새 문제가 된다.
  청킹 단위는 #73의 결정이다. 긴 조가 dense 점수에서 불리한지는 리포트에서 글자 수별로 본다

## 검색 세 가지

| run | 방법 |
| --- | --- |
| `bm25` | kiwipiepy 형태소. 체언·용언 어간·어근·외국어·숫자(`NN*` 중 `NNB` 제외, `VV`, `VA`, `XR`, `SL`, `SH`, `SN`)만 남긴다. Okapi BM25 `k1=1.2`, `b=0.75`를 직접 짠다 |
| `dense` | OpenAI `text-embedding-3-small`. 질문과 문서를 같은 모델로 임베딩, 코사인 유사도 전수 계산 |
| `hybrid` | 두 순위를 RRF로 합친다. `점수 = Σ 1/(60 + 순위)`. 88개 전체 순위를 쓴다 |

### 저장 — DB 없이 메모리에서

- 문서 88개라 전수 코사인이 1ms 단위다. pgvector로 정확 검색을 해도 결과는 같다
- 원래 설계(0727)가 pgvector를 고른 이유는 L4 공고 필터와 벡터를 한 쿼리에 넣는 것이다.
  이 티켓에는 필터가 없다. DB를 넣으면 비교에 보탤 정보 없이 마이그레이션만 는다
- BM25도 Postgres tsvector가 아니라 직접 짠다. `ts_rank`는 BM25가 아니라서(문서 길이 정규화가
  다르다) 「BM25와 비교했다」고 쓸 수 없게 된다. 88개면 수십 줄로 된다

### 임베딩 캐시

`data/cache/embed-<model>.jsonl` — 텍스트 sha256 → 벡터. 두 번째 실행은 API를 안 부른다.
같은 질문을 두 번 돌렸을 때 결과가 같은지(재현성)를 여기서 보장한다. `data/cache/`는 gitignore.

## 지표와 판정

질문마다 잰다. 평균만 남기면 같은 질문에서의 차이를 못 구한다(rag-lab 설계 §3 ①과 같은 이유).

| 지표 | 정의 |
| --- | --- |
| `recall@5` | 정답 조 중 상위 5개 안에 든 비율. **주 지표** |
| `hit@1` · `hit@5` | 정답이 하나라도 상위 1·5개 안에 있나 |
| `mrr` | 첫 정답 순위의 역수 |
| `gold_rank` | 정답 조마다 그 run에서의 순위 (리포트의 설명용) |

- **주 지표를 측정 전에 recall@5로 정한다.** 결과를 보고 지표를 고르면 차이가 있는 쪽을 고르게 된다
- k=5인 이유: 문서 88개에서 k=10이면 11%를 보여 주는 셈이라 쉬워진다. 정답이 2개 이상인 질문이
  42%라 hit보다 recall이 갈린다
- 판정: 문항별 차이로 paired permutation(10,000회, seed 고정) p값 + bootstrap 95% 신뢰구간

## 「이해가 된다」를 어떻게 보이나

리포트 `docs/131-dense-vs-hybrid.md` 한 장. 순서:

1. 요약 표 — 세 run의 지표 평균, dense 대비 hybrid 차이와 신뢰구간·p값
2. RRF 풀이 한 건 — 실제 질문 하나에서 정답 조의 BM25 순위·dense 순위가 어떻게 hybrid 순위가
   되는지 숫자로 계산해 보인다
3. 2×2 표 — `hit@5` 기준으로 둘 다 맞힘 / dense만 / hybrid만 / 둘 다 놓침 질문 수
4. 갈린 질문 전부 — 질문, 정답 조(제목), 정답의 BM25·dense·hybrid 순위, dense 상위 3개
5. 갈린 이유 묶음 — 갈린 질문을 「BM25가 끌어올림」 「BM25가 끌어내림」 등으로 센다
6. 정답 라벨 표본 20개와 분류별 인용 수 (위 §정한 것)
7. 질문에 `제N조`가 든 26쌍을 뺀 결과 — BM25가 숫자를 그대로 맞히는 질문이 결과를 끌고 가는지
