원래 #69는 최근 3년치 시행일 버전을 전부 쌓는 temporal 적재(`valid_from`/`valid_to`)였다. 2026-10-05에

날짜별 자격 판정(#78 as-of)에 필요한 것이라 그 티켓으로 미룬다.

### `조문.조문단위` 110개

- `조문여부` = `조문` 90 / `전문` 20
  - `전문`은 장·절 제목이다 (`제1장 총칙`, `제2장 입주자저축`, `제1절 …`). 뒤따르는 조문들의 소속이다
- 조문 90개 중 가지번호 있는 것(`제4조의2` 꼴) 27, 본문이 `삭제`로 시작하는 것 2
- 계층 개수 (조문 90개 아래): **항 304 · 호 504 · 목 169**

### 파싱에서 걸릴 자리 (실측)

| 자리 | 실측 |
| --- | --- |
| `항` 모양이 셋이다 | list 64 / **dict 14** (항 하나) / **없음 12** (본문이 `조문내용`에 바로 있음 — 제1·7·11·14·17조 …) |
| `호`·`목`도 같은 문제 | 하나면 dict로 올 수 있다(추정 — 항과 같은 직렬화). 코드가 list·dict·없음 셋을 다 받아야 한다 |
| 개정 이력이 본문에 섞여 있다 | 항 내용 끝에 `<개정 2016.5.19, … 2024.9.30, 2026.6.15>` |
| 가지 조문 | `조문번호`는 `4`이고 가지번호는 따로 온다. `제4조의2`를 `조문번호` 하나로 만들면 제4조와 겹친다 |

`<개정 …>`은 지우지 않고 따로 필드로 뺀다. #70 FAQ(2024-05-29 기준)의 인용 조문이 그 뒤에 개정됐는지
세는 데 그대로 쓸 수 있다 — 예: 제4조 ①항은 `2024.9.30`, `2026.6.15`에 개정됐다.

## 「제대로 파싱한다」를 무엇과 대조하나

**원본 JSON이 정답이다.** 원본 JSON의 텍스트 필드(`조문내용`·`항내용`·`호내용`·`목내용`)를 모두 모아
파싱 결과와 맞대면, 빠진 것·두 번 들어간 것이 0인지 기계로 센다. 세는 코드는 파서와 따로 짠다(같은
코드로 세면 같은 버그가 양쪽에 들어간다 — #70 목차 대조와 같은 이유).

개수 대조도 같이 한다: 조문 90 · 장절 20 · 항 304 · 호 504 · 목 169. 이 숫자는 이 문서가 확인한
값이고, 판본이 바뀌면 원본에서 다시 센 값과 맞댄다.

웹페이지(`law.go.kr/법령/주택공급에관한규칙`)는 조문을 자바스크립트로 불러와 HTML에 0개라 대조
원본으로 못 쓴다.

## 「API 키가 정상 작동한다」를 무엇으로 보나

`OC=test`는 공용 테스트 ID다. **jw 키(`LAW_OC`)로** 검색과 본문 두 호출이 정상 JSON을 돌려줘야 한다.
DRF는 키가 틀려도 HTTP 200에 오류 문구를 실어 보낼 수 있으므로(추정) 상태 코드만 보지 않고
`법령.기본정보.법령명_한글 == "주택공급에 관한 규칙"`까지 확인한다. `LAW_OC`가 비어 있으면
`OC=test`로 대신하지 않고 오류로 멈춘다 — 대신하면 이 기준이 조용히 통과한다.
