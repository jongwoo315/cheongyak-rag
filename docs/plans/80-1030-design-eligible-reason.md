# #80 세 번째 시도 — ELIGIBLE 이유가 프로필에 없는 값에 기대지 않게 한다

**Notion:** #80 · **이전 시도:** PR #12(닫음, 커밋 `1c06665`) · PR #13(닫음, 커밋 `f42b690`) · **바탕 설계:** `docs/plans/80-1029-design-axis-verdict.md` · **직전 설계:** `docs/plans/80-1030-design-eligible-guard.md`(축별 필요한 칸 표와 guard 위치를 그대로 쓴다)

## jw 기준

프로필에서 없는 이유로 eligible 판정을 하지 않는다

## 왜 다시 하나

PR #13은 jw 기준(빈 프로필 ELIGIBLE 0 · 꽉 찬 프로필 칸 없는 4개 축 ELIGIBLE 0)과 plan 구간을 모두 채웠지만 반려됐다(`docs/decisions.md` #80 재시작 행).

- 꽉 찬 프로필 청약통장 축 `ELIGIBLE` 4개 중 2개가 이유에 예치금·월납입금 기준을 충족했다고 썼다. #77 프로필에는 예치금·납입 칸이 없다
  - 예: 문수데시앙2단지 공가세대 일반공급 — 「제9조제3항의 월납입금 범위(2만원 이상 50만원 이하)를 판단할 수 있는 가입기간·예치금 기준상 청약통장 요건을 충족」
- 같은 일이 `partial.json`(생년월일·통장 가입일만 있는 프로필)에서도 났다. 통장 축 `ELIGIBLE` 5개 중 3개가 이유에 월납입금·예치금을 쓴다. PR #13 측정은 꽉 찬 프로필의 칸 없는 4개 축만 세서 이 값을 재지 않았다
- 원인: PR #13 guard는 통장 축에서 `savings_join_date` 하나만 봤다. 그런데 청약통장 순위 요건은 가입기간만이 아니다 — 민영주택은 지역별 예치금, 국민주택은 납입 횟수·금액을 같이 본다. 가입일만으로는 통장 요건을 다 채웠다고 할 수 없는데, guard가 그 상태에서 `ELIGIBLE`을 통과시켰다

## 무엇을 바꾸나

PR #13 코드를 그대로 가져오고 축별 필요한 칸 표 한 줄을 바꾼다.

| 축 | PR #13 | 이번 |
| --- | --- | --- |
| `account` | `savings_join_date` | **#77에 없음** — 가입일은 있지만 예치금(민영)·납입 횟수·금액(국민)이 없다 |
| 나머지 6개 축 | 그대로 | 그대로 |

- `account`는 프로필이 꽉 차도 `ELIGIBLE`이 나올 수 없게 된다. `need_info` 문구는 「청약통장 예치금(민영주택) 또는 납입 횟수·금액(국민주택)」
- `INELIGIBLE`은 그대로 둔다. 가입기간이 모자라면 예치금을 몰라도 미달이다 — 요건 하나가 어긋나면 `INELIGIBLE`은 맞고, `ELIGIBLE`은 요건이 전부 맞아야 한다
- system 프롬프트를 고치지 않는다. 캐시 135개를 그대로 읽어 API 호출 0회가 기대값이다

## 설계 결정

| 항목 | 고른 것 | 안 고른 것과 이유 |
| --- | --- | --- |
| 통장 축을 막는 방법 | 축별 필요한 칸 표에서 `account`를 「#77에 없음」으로 | 이유 문장에 「예치금」「납입」이 나오면 막기. 문장 검사는 단어를 안 쓰고 같은 주장을 하면 통과한다. 가입일만으로 통장 요건을 다 채웠다고 할 수 없다는 것은 문장과 상관없는 사실이다 |
| 프로필에 예치금 칸 더하기 | 안 한다 | #82 범위다. 칸을 더하면 프로필 3종과 측정 표본이 바뀐다 |
| system 프롬프트 | 고치지 않는다 | PR #12에서 세 번 고쳐도 값이 오르내렸다. 그대로 두면 LLM 원 판정이 PR #12·#13과 같아 표 한 줄의 효과만 따로 보인다 |

## 측정 — jw 기준을 어떻게 재나

guard 규칙과 **다른 방법으로** 잰다. 규칙과 같은 표로 재면 규칙이 틀릴 때 측정도 같이 틀린다.

- 대상: 세 프로필 전부의 최종 `ELIGIBLE` 판정
- 방법 1 — 이유 문장 검사: 이유에 #77 프로필에 없는 값을 가리키는 말이 나오는지 센다. 단어 목록은 프로필에 없는 사실에서 정한다 — `예치금` `납입` `거주` `소득` `자산` `당첨`
  - 목록은 PR #12·#13 이유를 보고 정했다. 이 측정 데이터에 맞춘 목록이라 처음 보는 표현은 놓칠 수 있다
- 방법 2 — 이유 원문 전부: 최종 `ELIGIBLE`의 공고·프로필·축·이유 원문을 리포트에 전부 싣는다. 사람이 읽고 판정할 수 있게 한다
- 같이 적는 값: 이유가 「~라는 정보가 없어」처럼 값이 없는 것을 근거로 드는 문장 수
  - 예(PR #13 꽉 찬 프로필 무주택 축): 「homeless_now=true와 ever_owned=false, 그리고 제53조상 예외 사유에 해당한다는 정보가 없어 … 무주택세대구성원으로 볼 수 있습니다」
  - 이 판정은 `homeless_now`라는 프로필 값에 기대고 있고, 없다는 사실은 덧붙인 말이다. 이게 jw 기준에 걸리는지는 정하지 않는다 — 값만 적는다

## 결과를 읽을 때

- `account` 최종 `ELIGIBLE` 0은 표 정의상 나오는 값이다. LLM 원 판정의 통장 축 `ELIGIBLE`(PR #13 꽉 찬 4 · 일부 5)은 guard 전 값으로 따로 보인다
- 남는 `ELIGIBLE`은 꽉 찬 프로필의 무주택·세대주 축뿐일 것으로 본다(PR #13 기준 6 + 2). jw 기준은 이 판정들의 이유로 판정된다
- 꽉 찬 프로필에서 판정을 내린 비율은 내려간다. PR #13은 무주택·통장 12개 중 10개였는데 통장 축은 이제 `ELIGIBLE`을 낼 수 없다
