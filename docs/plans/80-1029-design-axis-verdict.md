# #80 축별 판정과 guardrail — 설계

**Notion:** #80 · **선행:** #79(축별 검색), #77(프로필 정규화), #139(답 생성) · **상위 설계:** `docs/plans/0727-design-cheongyak-rag.md` §4·§5 B6·B7

## jw 기준

7축에서 필요한 것만 골라 검색을 하고 5가지 판정값 중 하나로 결과를 보여준다, 그리고 판정의 근거가 있는지도 확인하다

## 무엇을 만드나

공고 하나와 프로필 하나를 받아, #79가 켠 축의 하위 질의마다 판정 하나를 낸다.

```
공고 ──▶ axes.plan ──▶ 켜진 축 ──▶ axes.search ──▶ 하위 질의마다 조문 5 + FAQ 3
프로필 ─▶ profile.score(공고일 기준) ─┐                         │
                                        ▼                         ▼
                              B6 판정 LLM(요건 정의 + 프로필 값 + 근거) → 판정 + 인용
                                        │
                              B7 guardrail ─┬─ 근거 0개 → LLM을 부르지 않고 UNVERIFIABLE
                                            ├─ 문맥에 없는 라벨 인용 → 기각(invalid_citations)
                                            ├─ 남은 인용 라벨을 chunks 테이블에서 다시 조회 → 없으면 기각
                                            └─ 판정이 UNVERIFIABLE이 아닌데 남은 인용 0개 → UNVERIFIABLE로 바꾼다
```

- 꺼진 축은 LLM을 부르지 않는다. 출력에 「꺼짐 — 이유」만 남는다
- `special_type` 축은 특별공급 유형마다 하위 질의가 하나라서 판정도 유형마다 하나다. 축 하나로 합치는 것은 #81(집계)이 한다

## 판정값 5개 (상위 설계 §4 그대로)

| 값 | 뜻 | 따라오는 칸 |
| --- | --- | --- |
| `ELIGIBLE` | 요건을 채운다 | — |
| `INELIGIBLE` | 요건을 못 채운다 | `reason` |
| `CONDITIONAL` | 조건이 붙으면 채운다 | `conditions` |
| `NEED_INFO` | 프로필 정보가 모자라 판정을 못 한다 | `need_info`(무엇을 물어야 하나, 문장) |
| `UNVERIFIABLE` | 근거를 못 찾았거나 규칙끼리 부딪힌다 | `reason` |

## 설계 결정

| 항목 | 고른 것 | 안 고른 것과 이유 |
| --- | --- | --- |
| 위치 | `generate/verdict.py`(판정), `generate/verdict_report.py`(측정) | 새 패키지. #139의 캐시·재시도·비용 상한·`HardApiError`를 그대로 가져다 쓰려면 같은 패키지가 낫다 | <!-- style-exempt -->
| 모델 | `settings.openai_gen_model`(`gpt-5.4-mini`) | 상위 설계는 판정에 `gpt-5.6-sol`을 적었다. 가격 표(`answer.PRICE_PER_1M`)에 mini만 있고, 모델 비교는 #143이 따로 한다. 지금 바꾸면 비교할 기준이 없다 |
| 출력 강제 | JSON schema `strict: true` — `verdict` enum 5값, `reason`, `conditions[]`, `need_info[]`, `citations[]` | 자유 텍스트를 파싱. #139가 schema로 파싱 실패를 없앴다 |
| 인용 실재 대조 | ① 문맥 라벨 안에 있나(#139 방식) ② 남은 라벨을 `chunks`에서 다시 조회(조문은 `source='law' AND law_mst=공고 MST`, FAQ는 `source='faq'`) | ①만 쓰기. 문맥 라벨이 원래 DB에서 왔으니 ②는 같은 답을 낼 것이다. 그래도 상위 설계 B7이 「L1 실재 대조」를 따로 적었고, 라벨 문자열이 검색 단계와 어긋나는 사고(공백·괄호)를 잡는다. 쿼리 하나라 싸다 |
| 인용이 필요한 판정 | `UNVERIFIABLE`을 뺀 4개 전부. `NEED_INFO`도 「어느 규정이 그 정보를 요구하나」를 인용한다 | `NEED_INFO`는 인용 없이 허용. 그러면 LLM이 근거를 못 찾을 때 `NEED_INFO`로 빠져나가 `UNVERIFIABLE`과 섞인다 — 상위 설계가 둘을 가른 이유가 사라진다 |
| 프로필 값 | `Profile.to_dict()` 원본 + `profile.score(p, 공고일).to_dict()`의 `values`·`scores`·`missing` | 원본만. 무주택 기간·통장 가입기간은 #77이 날짜 계산을 끝내 둔 값이라 LLM이 다시 셈하지 않게 한다 |
| 공고 값 | 공고명·지역·규제 표시 넷·특별공급 세대수·공고일 | — |
| 프롬프트 순서 | system(판정 규칙 + 축 요건 정의)이 앞, 공고·프로필·근거가 뒤 | 상위 설계 §6 캐싱 규칙. 캐시 적중을 재는 것은 이번 범위 밖 |
| 캐시 | `data/cache/verdict-<model>.jsonl`, 키 `sha256(model + system + user)` | `gen-` 캐시에 섞기. 질문 꼴이 달라 섞어도 충돌은 없지만 파일을 나눠야 지울 때 판정만 지울 수 있다 |

## 프로필에 없는 칸

#77 `Profile`에는 거주지역·거주기간·소득·자산·재당첨 이력·특별공급 유형별 자격 칸이 없다. 그래서 `residence`·`income_asset`·`rewin`·`special_type` 축은 프로필이 꽉 차도 `NEED_INFO`가 정상 답이다.

- 이번에 칸을 더하지 않는다. 어떤 칸을 어떤 꼴로 물을지는 #82(결손 분석 + 질문 랭킹)가 `NEED_INFO` 결과를 보고 정한다
- 측정에서는 이 네 축의 `NEED_INFO` 비율을 따로 적는다. 프로필이 꽉 찬 경우에도 이 축에 `ELIGIBLE`·`INELIGIBLE`이 나오면 LLM이 없는 정보를 지어낸 것이다

## 이번에 안 하는 것

- 축 판정을 공고 하나의 전역 판정으로 합치기 — #81
- `NEED_INFO` 질문 페이로드(어떤 칸 / 왜 / 어디서 확인 / 답하면 뭐가 바뀌나)와 질문 순서 — #82
- 판정이 맞았는지 정답과 대조 — 골든셋(#75)·eval(#76)이 없다. 이번에는 「판정값이 5개 중 하나이고, 인용이 실제로 있다」까지만 잰다
- 인용한 조문이 판정 내용을 실제로 뒷받침하는지 — 사람이 표본을 읽는다. 자동으로는 안 잰다
- 프롬프트 캐시 적중률, 모델 비교(#143), trace 저장(#83)
- 프로필 칸 추가

## 열린 질문 (루프가 정하고 리포트에 적는다)

1. `special_type`처럼 하위 질의가 여럿인 축에서 근거가 겹치면 판정을 한 번에 묻는 편이 나은가 — 이번에는 하위 질의마다 따로 묻는다. 결과가 유형마다 같게 나오면 리포트에 그 사실만 적는다
2. `CONDITIONAL`과 `NEED_INFO`가 갈리는 지점 — 「정보만 있으면 판정된다」는 `NEED_INFO`, 「공고 이후 행동(전입·해지 등)이 있어야 채운다」는 `CONDITIONAL`로 system 프롬프트에 적는다. 표본에서 이 규칙대로 갈렸는지 리포트에 사례를 싣는다
