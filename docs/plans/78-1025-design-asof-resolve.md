# #78 as-of 해소(B3) — 설계

**Notion:** #78 · **Tier:** C · **작성:** 2026-10-25

## jw 기준

공고별로 유효한 법령 버전을 확인할 수 있다

## 목적

판정(설계 `docs/plans/0727-design-cheongyak-rag.md` §5 B3)은 공고의 모집공고일에 유효했던 「주택공급에 관한 규칙」으로
해야 한다. 지금 repo에는 현행 1버전(`data/raw/law-008243-20260615.json`)만 있고, 공고(#71, `notices` 테이블)와 법령을
잇는 것이 없다. 이번 티켓은 규칙의 시행일별 버전 목록을 DB에 넣고, 공고마다 그날 유효한 버전 하나를 고르는 규칙을
SQL view로 만든다. #69가 「과거 버전은 #78」로 미뤄 둔 것이 여기다(`docs/plans/69-1005-design-law-parse.md:11-13`).

## 착수 때 확인한 사실 (2026-10-25, main 세션 실측)

- 버전 목록: `lawSearch.do?target=eflaw&query=주택공급에관한규칙&display=100&page=N`. 응답 `totalCnt` 177은 이름이 비슷한
  다른 법령까지 센 값이고, `법령명한글 == "주택공급에 관한 규칙"`인 행은 2페이지에 걸쳐 **129행**이다
  - 행 하나 = (법령일련번호 MST, 시행일자). MST는 104개다 — **같은 MST가 시행일 둘 이상으로 나온다**(부칙의 단계 시행.
    예: MST 265605가 시행일 2024-10-01과 2024-11-01로 두 행)
  - **같은 시행일에 MST가 둘 이상인 날이 7개다**: 2024-07-01·2024-03-25·2023-04-01·2017-01-01·2015-02-27(3개)·
    2014-06-30·2008-01-01. 예: 2024-07-01에 MST 261483(공포 2024-03-25)과 257091(공포 2023-12-20)
  - 가장 오래된 시행일 2005-03-09, 최신 2026-06-15(`현행연혁코드` 현행 1행, 나머지 128행 연혁). 시행 예정 행은 없다
  - 행 키: `법령일련번호` `시행일자` `공포일자` `공포번호` `법령ID`(008243) `제개정구분명` `현행연혁코드` 등 16개
- 본문 조회: `lawService.do?target=eflaw&MST=<MST>&efYd=<시행일>&type=JSON`이 그 버전 본문을 준다
  (MST 265605 + efYd 20241001 → `시행일자 20241001 · 공포번호 01391`)
  - **`ID=8243&efYd=<날짜>`는 빈 객체 `{}`를 준다** — 시행일과 정확히 같은 날짜를 줘도 같다. 법제처 API에는
    「이 날짜에 유효한 버전을 달라」는 조회가 없다. 그래서 고르는 규칙은 우리가 만든다
  - `ID=8243`만 주면 현행 버전을 준다
- 공고: `notices` 84행, 모집공고일 2026-07-27 ~ 2026-10-23. **전부 현행 시행일(2026-06-15)보다 뒤다.** 규칙이 맞으면
  84건 전부 MST 286965(시행 2026-06-15)로 정해진다 — 결과가 한 버전뿐인 것은 정상이다
- 키는 `.env`의 `LAW_OC`(설정 `settings.law_oc`). `law.py`가 이미 OC를 응답·예외에서 가리는 `_snippet`을 쓴다

## 1. 고르는 규칙

공고 하나의 모집공고일 D에 대해:

1. 시행일 ≤ D인 행만 남긴다 (시행일 당일부터 적용)
2. 그중 시행일이 가장 늦은 것
3. 같은 시행일에 MST가 둘 이상이면 공포일이 가장 늦은 것, 그래도 같으면 MST가 큰 것

3번의 근거: 같은 날 시행되는 두 MST 중 늦게 공포된 쪽이 앞 개정의 단계 시행분까지 반영한 본문이다(2024-07-01:
261483은 257091 뒤에 공포됐다). **이 판단은 이번에 검증되지 않는다** — 본문 대조는 고른 버전이 실제로 있는지만 보고,
지금 공고 84건은 이런 날에 걸리지 않는다. 테스트로 규칙이 그렇게 동작하는지만 고정한다.

D보다 이른 시행일이 없으면(2005-03-09 이전 공고) 버전을 정하지 않는다 — NULL로 두고 센다.

## 2. 설계 결정

| 결정 | 고른 것 | 안 고른 것과 이유 |
| --- | --- | --- |
| 저장 | Postgres `law_versions` 테이블 + `notice_law_versions` view | jsonl 파일은 공고(DB)와 join하려면 앱 코드가 필요하다. view면 jw가 SQL 한 줄로 공고별 버전을 본다. 다음 단계(B4 pre-filter)도 SQL에서 이어 붙는다 |
| 키 | PK `(law_id, mst, effective_date)` | 실측에서 MST만으로도, 시행일만으로도 유일하지 않았다 |
| 고르는 위치 | view 안 SQL (`DISTINCT ON` 또는 `LATERAL … ORDER BY effective_date DESC, promulgation_date DESC, mst DESC LIMIT 1`) | 파이썬 함수로 두면 view와 규칙이 두 벌이 된다. 리포트·테스트도 view를 읽는다 |
| 버전 범위 | 129행 전부 넣는다 | 2페이지·2회 호출이라 거를 이유가 없다. 공고 기간을 넓혀도(`--months`) 다시 받을 필요가 없다 |
| 본문 | **이번에 파싱해 넣지 않는다.** 정해진 버전마다 본문을 한 번 받아 시행일자·공포번호만 대조하고 raw JSON을 `data/raw/law-008243-<시행일>.json`으로 둔다(이미 있으면 받지 않는다) | 조문을 판정에 쓰는 것은 #79·#80이다. 지금 공고는 전부 현행 1버전이라 새로 받을 본문이 0개다 |
| 재실행 | `ON CONFLICT DO UPDATE` + `fetched_at` | #71과 같다 |
| 테스트 DB | 기존 `tests/conftest.py`의 테스트 DB 방식 그대로 | #71이 만든 것을 쓴다 |

## 3. 지표

| 지표 | 정의 |
| --- | --- |
| 버전이 정해진 공고 | `notices` 전체 중 view에서 MST가 NULL이 아닌 공고 수 |
| 본문 대조 | view에 나온 서로 다른 (MST, 시행일)마다 `lawService` 본문을 받아 `기본정보.시행일자`·`공포번호`가 `law_versions` 행과 같은 비율 |
| 목록 완결성 | 받은 행 수(이름 일치) · 페이지 수 · 가장 오래된 시행일 ≤ 가장 이른 모집공고일인가 · (MST, 시행일) 중복 0 |
| 같은 날 여러 MST | 그런 시행일 수와, view가 그중 무엇을 골랐는지 |
| 호출 | 목록 페이지 수 + 본문 조회 수 |

baseline 없음 — 첫 측정이다.
