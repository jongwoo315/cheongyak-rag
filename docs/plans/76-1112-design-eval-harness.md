# #76 Eval harness — 설계

**Notion:** #76 · 브랜치 `feat/76-eval-harness` · 바탕 설계 `docs/plans/0727-design-cheongyak-rag.md` §7

## 1. 무엇을 만드나

골든셋(#75 `runs/75/golden.jsonl`, 문항 50개 · 정답 라벨 524개)을 지금 배포된 판정 흐름에 그대로 돌리고,
하위 질의마다 시스템 결과와 정답 라벨을 맞춰 지표를 낸다. 결과는 `runs/76/`과 리포트 `docs/76-eval.md`에 남는다.

이 repo에는 판정 화면까지 끝까지 도는 흐름이 이미 있다(#85). 없는 것은 **측정 흐름**이다 —
골든셋 → 판정 → 정답과 비교 → 리포트. 이 티켓이 그 흐름을 처음 만든다.

## 2. jw 기준

「청약공고 질의에 대한 검색을 완료하고, 검색결과에 대한 판정 기준을 세울 수 있다」
(되물은 뒤: 「내가 말한 판정기준은 eval harness 쪽이었어」)

- 「검색을 완료」 — 정답 라벨 524개 각각에 대해, 시스템이 같은 하위 질의를 만들고 검색까지 돌았나
- 「판정 기준을 세울 수 있다」 — 바탕 설계 §7 지표가 골든셋과 대조한 값으로 나와서, jw가 그 값을 보고
  통과 기준(임계값)을 정할 수 있나. 임계값을 정하는 것은 이 티켓이 아니다 — 첫 측정이라 baseline이 없다

## 3. 설계 결정

### 3.1 무엇을 돌리나 — 배포와 같은 함수

`generate.verdict.judge`를 공고·프로필마다 부른다. 모델은 배포와 같은 `settings.openai_gen_model`
(지금 `gpt-5.4-mini`), k=5 · faq_k=3도 배포 기본값 그대로. API의 `trace.run_traced`는 부르지 않는다 —
`traces` 테이블에 행을 쓰고 하루 판정 한도를 센다. `judge`는 DB를 읽기만 한다.

판정 흐름 코드(검색·프롬프트·guard)는 고치지 않는다. 지금 시스템을 재는 것이 목적이다.

### 3.2 하위 질의 맞추기

정답 라벨과 시스템 판정을 `(문항 id, axis, query)`로 맞춘다. #75 `golden.check`가 정답 라벨의 query가
`axes.plan`이 만드는 문장과 같다는 것을 이미 확인했다. 못 맞춘 정답 라벨은 지표 분모에 남기고
따로 센다(빼면 지표가 좋아 보인다).

### 3.3 지표 — 바탕 설계 §7 중 다섯

| 지표 | 정의 | 분모 |
| --- | --- | --- |
| recall@5 | 정답 근거 조문(조 라벨) 중 시스템 조문 검색 top-5에 든 것의 비율. (라벨, 조) 쌍을 모두 모아 센다 | 정답 근거 조문 쌍 전체 |
| hit@5 | 정답 근거 조문이 하나라도 top-5에 든 정답 라벨의 비율 | 정답 라벨 524 |
| citation precision | 시스템이 인용한 조문 라벨 중 그 하위 질의의 정답 근거 조문에 있는 것의 비율. FAQ 인용(`Q47` 꼴)은 정답에 없으니 빼고 수만 따로 센다 | 시스템 조문 인용 전체 |
| 판정 정확도 | 시스템 최종 판정값이 정답 라벨 판정값과 같은 비율. 축 7개마다 + 전체 | 정답 라벨(축별) |
| 치명오답률 | 정답이 `INELIGIBLE`인 라벨 중 시스템이 `ELIGIBLE`을 낸 비율. 바탕 설계가 단일 최중요 지표로 둔 것 | 정답 `INELIGIBLE` 91 |
| 정당 abstain 비율 | 정답이 `NEED_INFO`인 라벨 중 시스템도 abstain한 비율 | 정답 `NEED_INFO` 378 |
| 부당 abstain 비율 | 정답이 `ELIGIBLE`·`INELIGIBLE`인 라벨 중 시스템이 abstain한 비율 | 정답 `ELIGIBLE`·`INELIGIBLE` 146 |

- abstain = 시스템 최종 판정이 `NEED_INFO` 또는 `UNVERIFIABLE`. 둘 다 「판정을 내리지 않음」이다.
  정답 라벨에는 `UNVERIFIABLE`·`CONDITIONAL`이 없다(#75 분포)
- 시스템 판정이 실패한 하위 질의(`Verdict.error`)는 판정 정확도에서 틀림으로, abstain에서는 abstain이 아닌 것으로 센다.
  수는 따로 낸다
- 「최종 판정」은 인용 대조·ELIGIBLE guard까지 거친 값이다(배포 화면이 보여 주는 값). guard 전 값은 run 파일에 남기기만 한다
- 바탕 설계 §7의 `NEED_INFO` 정밀도와 확정까지의 질문 수는 이번에 안 한다(§5)

### 3.4 저장 — 다시 셀 수 있게

- `runs/76/run.jsonl` — 하위 질의 한 줄: 문항 id · axis · query · 정답 판정값 · 정답 근거 조문 · 시스템 최종/guard 전 판정값 ·
  인용 · 조문 top-5 라벨 · FAQ top-3 라벨 · 오류 · 비용 · cached. 지표는 이 파일만으로 다시 셀 수 있어야 한다
- `runs/76/metrics.json` — 지표 값과 분자·분모
- `docs/76-eval.md` — 리포트. 지표 표, 축별 판정 정확도 표, 치명오답 라벨 전부(문항·하위 질의·이유), 정답과 시스템의 판정값 표(5×5)

### 3.5 측정을 측정 코드가 따로 다시 센다

리포트를 쓰는 측정 코드는 `runs/76/run.jsonl`을 읽어 지표를 **harness 지표 함수를 부르지 않고** 따로 계산하고,
`metrics.json`과 다른 지표 수를 센다. 같은 함수를 부르면 같이 틀린다(#83 리뷰 defer와 같은 문제).

### 3.6 비용·재현성

- 하위 질의 524개 = LLM 호출 최대 524회. #80 실측이 135회 $0.93이라 약 $3.6로 본다. 상한 `--budget-usd 10` <!-- style-exempt -->
- 응답은 `data/cache/verdict-<model>.jsonl` 캐시에 덧붙는다. 같은 명령을 두 번째 돌리면 호출 0회여야 하고 지표가 같아야 한다

## 4. 지표를 읽는 법 — 리포트에 그대로 적는다

- 정답 라벨은 #75에서 라벨 규칙 문서를 스크립트로 옮겨 붙였고 jw 표본 20개가 20/20 맞았다. 지표는 「골든셋과 얼마나 맞나」이지
  「법적으로 맞나」가 아니다
- 정답 라벨의 72%(378/524)가 `NEED_INFO`다. 판정 정확도 전체 값은 `NEED_INFO`를 맞힌 것이 대부분을 차지한다 — 축별·판정값별 표를 같이 본다
- 거주·소득자산·재당첨 축은 정답이 전부 `NEED_INFO`다(프로필에 칸이 없다)

## 5. 이번에 안 하는 것

- 지표 임계값 정하기 — 이 측정 결과를 보고 jw가 정한다
- 판정 흐름 개선(검색·프롬프트·guard). 측정에서 문제가 보여도 고치지 않고 리포트에 적는다
- `NEED_INFO` 정밀도, 확정까지의 질문 수 — 시스템이 묻는 칸 이름이 정답의 `need`와 같은 이름 체계가 아니다(#75 리뷰 #17)
- 골든셋 수정 — 정답 라벨이 틀려 보이면 리포트에 적기만 한다
- CI 연결, 배포 사이트에 돌리기
