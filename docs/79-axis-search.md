### 읽는 법

- 1번 켜진 축 목록 대조: `axes.plan`의 켜짐 여부와, 이 측정 코드가 `notices`·`notice_models`를 SQL로 직접 읽어 따로 계산한 켜짐 여부를 비교했다. 두 쪽을 같은 사람이 같은 설계에서 옮겨 적었으므로 같이 틀릴 수 있다
- 2번 기대 조는 main 세션이 구현 전에 조 제목만 보고 정했다. 정답 대조가 아니라 「이 질의가 그럴듯한 조를 찾는가」를 보는 확인이다. 축 하나의 하위 질의가 여럿이면 전부에서 들어야 「든 축」으로 센다
- 3번은 DB 경로(dense=`nearest`, BM25=앱, 합치기=`rrf`)와 메모리 경로(`query.Index`)가 같은 하위 질의에서 조문 상위 5개·FAQ 상위 3개 집합이 같은지다. 순서는 보지 않는다
- 공고가 가리킨 법령 버전(MST)은 286965이다. 3번의 메모리 `Index`는 법령 파일 하나(시행 2026-06-15)로 만들어서, 버전이 둘 이상이면 다른 버전 공고는 견주지 못한다
- 2번 `special_type`의 기대 조는 제35조~제47조 특별공급 조 15개(제35조의2·제35조의3 포함, 제47조의3 제외)라 특별공급 질의가 들기 쉽다. 8/9는 검색 품질의 증거가 아니라 질의가 특별공급 조로 간다는 확인이다
- 5번 시간은 공고마다 `load_facts`부터 `search`까지다. BM25 색인은 (source, MST)마다 처음 한 번 만들고 그 시간(1.498초)은 공고별 시간에서 뺐다. 하위 질의 임베딩은 시간 재기 전에 한 번에 보냈다
- 1·3번의 dense 경로는 `chunks` 행이 568개라 planner가 HNSW 대신 전수 스캔(Seq Scan)을 고르고, 공고가 가리킨 MST가 하나라 `law_mst` 조건이 행을 거르지 않는다. HNSW 후보에서 거르는 경우(필터 × ANN)는 이 실행에서 재지 못했다

## 5. 열린 질문에서 고른 것 (설계 §2·§7)

- `householder`(세대주 여부)의 켜는 조건을 설계 §2의 「항상」에서 바꿨다. 제28조제1항제1호다목은 「세대주일 것」을 투기과열지구·청약과열지역에서만 요건으로 건다(가목 수도권·나목 수도권 외·라목 위축지역에는 없다). 제27조도 같다. 특별공급에서 세대주를 한정하는 곳은 제46조(노부모 부양 — 무주택세대구성원은 세대주에 한정)다. 그래서 투기과열지구·청약과열지역 표시가 하나라도 참이거나 노부모 부양 특별공급 세대수가 0보다 크면 켠다. 제43조(생애최초)의 「세대주」는 면적 구분에 쓰이는 낱말이라 조건에 넣지 않았다
- `rewin`(재당첨제한)의 켜는 조건은 설계 그대로 두었다. 제54조제1항은 분양가상한제 적용주택(3호)·투기과열지구(6호)·청약과열지역(7호) 공급 주택에 당첨된 세대를 제한한다. 본문에 「공공택지」라는 낱말은 없어서 이 표시를 켜는 조건에 넣은 근거는 확인하지 못했다(공공택지 표시가 참이면 분양가상한제 적용 대상인 경우가 많을 것으로 본다 — 추정). 제54조는 분양전환공공임대(4호)·토지임대주택(5호)·이전기관 특별공급(2호)에도 걸리는데, 이는 공고의 규제 표시 칸으로는 알 수 없어서 켜는 조건에 넣지 않았다. 그래서 이 축이 꺼진 공고도 이 조가 적용될 수 있다
- `residence`는 설계대로 항상 켠다. 제4조는 주택건설지역 거주 요건(제1항)과 거주기간 우선공급(제5항)을 정하고 투기과열지구 여부에 따라 달라지지만, 공고마다 달라지는 것은 하위 질의에 끼우는 공급지역명뿐이다
- `special_type`은 특별공급 세대수 합이 0보다 큰데 유형별 세대수가 전부 0이면 유형을 모르므로 유형 이름 없는 문장 하나로 검색한다
